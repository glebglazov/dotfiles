membr · a plan for a change, not yet in the code

To keep an epoch until 220k tokens, change one constant from 150,000 to 220,000

Question: what must change so that membr keeps an epoch until it reaches 220k tokens, not 150k?

Answer: set EPOCH_BUDGET in packages/protocol/src/index.ts to 220_000. The server trigger and the status in both clients all read the limit from epochLimit(), so only tests, docs and one tooltip text change with it.

Catch: the limit stays 80% of the window when that is less. So you get 220k only on models with a window of 275,000 tokens or more. A 200,000-token window goes from 150k to 160k.

Two decisions need you: D1 — constant or setting and D2 — what a small window gets. You answer them at the end, in Decisions.

1. The status shows the limit, so you see the change first in the header

The header of the web client shows how full the epoch was after its last turn. The terminal client shows the same words. The same turn (42,000 tokens used) gives these texts. The numbers are from the e2e tests; the 1M window is illustrative.

Today (limit 150k)

membr.Readyepoch 42k / 150k (28%)

Both a 200,000 and a 1,000,000 window show this text.

After the change

membr.Readyepoch 42k / 220k (19%)

Window 1,000,000 → 220k.

membr.Readyepoch 42k / 160k (26%)

Window 200,000 → 160k (80% of the window).

The Settings popover shows the same limit in full: "42,000 of 150,000 tokens" becomes "42,000 of 220,000 tokens", or "of 160,000" on a 200,000 window. On screens under the phone breakpoint, the web header hides this text.

2. One function computes the limit, and every place that uses it calls that function

The limit lives in the protocol package. The server uses it to decide on a new epoch. The core package uses it for the status words, and both clients show those words. No other code has the number 150,000.

The server sends context to the clients in the state event. Each client computes the limit itself from context.window, so the server sends no limit. A new server with an old client would show the old 150k; both ship from this repository at once.

D1 — Keep the budget a constant, or make it a setting in config.json?

The goal names one number. A setting would let each agent pick its own.

Recommendation: A. The limit is a property of how models read long context, not of one agent. A setting adds a protocol field and a second source of truth for a number nobody asked to vary.

open

3. The new limit is 220k only when the window is 275,000 tokens or more

The 80% rule stays. It was added so that the next turn still fits in a small window (see docs/p0-report.md, section 9). With a budget of 220,000, the budget wins only when 80% of the window is at least 220,000: a window of 275,000 or more. Today that point is 187,500.

D2 — What limit does a window under 275,000 tokens get?

With the formula as it is, a 200,000 window moves from 150k to 160k. That is not the 220k of the goal, and it is more than today.

Recommendation: A. The 80% rule is the guard against an overflow, and an overflow costs a failed turn. The goal is about the size of an epoch on large windows, where A gives exactly 220k.

open

4. A turn that ends at or over the limit marks the epoch, and the next turn opens a new one

The same turns run before and after the change, on a 1,000,000 window. The token counts are illustrative.

The rule, from turn.ts: on ended, full(context) sets reopen: true. When the chat goes idle with that mark, membr closes the epoch and opens a new one from the view. If a message arrives before that step, its start does the same before it sends the message. Only the number in the comparison moves. Two other paths do not change:

  • Overflow. A turn that Claude Code or the API refuses for size ("Prompt is too long") still fails, gets a new epoch, and a note asks the user to send the message again.
  • Summary batch. It still runs when the view is over 128 KB (View.over), and still starts a new epoch. It counts view bytes, not epoch tokens.
What a larger epoch costs

Each request in an epoch sends the whole epoch again, mostly from the prompt cache. The README says that past the limit "each request costs more and the model reads its context less well". The commit that set 150k (d140d0c) cites practitioners who put that zone at about 100k to 150k tokens. 220k accepts more cost per request in exchange for fewer new epochs, and each new epoch's first turn reads the view without the cache.

5. The change is one constant, and the tests, docs and tooltip that name 150k follow it

No logic changes. turn.ts, core/src/index.ts and term/src/transcript.ts stay as they are, because they call epochLimit().

  • packages/protocol/src/index.ts code — the constant.
  • packages/web/src/main.ts:158 text — the Settings tooltip says "150k tokens".
  • packages/server/context.test.ts:51–52 test — the large-window rows move to 220,000 and 219,999. The small-window rows (120,000 of 150,000) stay: they test the 80% rule.
  • packages/web/test/browser.e2e.ts:77, 80 and packages/term/test/pty.e2e.ts:56 test — their fake window is 200,000, so the expected text becomes 160k. I recommend that they use a 1,000,000 window, so that the e2e tests show 220k and the 80% path stays in context.test.ts.
  • README.md:248–251 and CONTEXT.md:36 docs — 150k becomes 220k, and "under 187,500 tokens" becomes "under 275,000 tokens".
